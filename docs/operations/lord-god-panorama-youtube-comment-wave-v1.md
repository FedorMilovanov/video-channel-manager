# «Панорама Библии» — защищённая публикация комментариев через Wave Engine

**Проект:** `lord-god-strength` · **GitHub:** issue #795 · **YouTube owner:** `UCeSJsC6go2c9pdJCuUI1BYA` · **OAuth alias:** `fedor-milovanov`.

## Назначение и ограничения

Модуль `wave_engine/youtube_comment_provider.py` регистрирует **только** операцию `youtube.comment.create` с policy `lord-god-panorama-comment-wave-v1`. Путь выполняет один заранее рассмотренный комментарий для одного публичного видео; он **не публикует автоматически** черновики и не возрождает завершённый `scripts/apply_youtube_comment_plan.py`.

Исходный файл с точным рассмотренным payload должен быть зафиксирован в `WaveSourceEvidence` как единственный артефакт с именем `panorama-reviewed-comment.json` (в произвольном безопасном относительном каталоге); другие доказательства могут быть отдельными артефактами. Этот JSON содержит ровно восемь полей операции без дополнительной обёртки. Перед API-запросом адаптер проверяет принадлежность source snapshot, проекта и политики операции, SHA-256 фактически прочитанных байтов файла, отсутствие повторяющихся JSON-ключей и точное равенство всех полей payload источнику. Нельзя обосновать изменённый текст чужим или лишь формально SHA-связанным файлом. Это контроль целостности, не криптографическая подпись редактора: источник и полный однооперационный план всё равно требуют отдельной подлинной приёмки. CLI является поддерживаемым путём записи с журналом; внутренний адаптер не является самостоятельным операторским интерфейсом. Затем строятся строго типизированные `WavePlan` и `WaveApplyIntent`, связанные с его SHA-256 и проектом. CLI `video-manager wave apply` допускает этот провайдер только при **одной** операции, двух подтверждениях `--enable-provider-writes` и `intent.enable_provider_writes`. Для этого адаптера CLI полностью запрещает `apply` в CI, даже при наличии операторского токена: необходим постоянный owner runtime с сохранённым индексом резервирований. Общая CI-политика Wave Engine для других адаптеров не меняется. Реальный `YouTubeCommentWriter` также отклоняется при прямом вызове `execute` в CI до обращения к API, не только через CLI. Инициализация требует идентифицируемого Cloud project из OAuth Desktop client и абсолютного корня данных; ошибки конфигурации возвращают код 3 до создания журнала. GET-only reconciliation не выдаёт разрешения на POST.

Перед исполнением сверяются: точный `channel_id`, единственная OAuth-принадлежность по `channels.list(mine=true)`, полное текущее название и публичность видео, правильный первоисточник `slovo.org`, контрольная сумма уже одобренного комментария, отсутствие любых авторских top-level комментариев на видео. Используется общий локальный замок YouTube, чтобы два писателя не работали одновременно. Приложение повторно проверяет запись по данным владельца.

Каждая операция получает собственный журнал `WaveEngine` **до начала возможной отправки POST**. Если исход отправки или постпроверки неизвестен, автоматическое повторение запрещено. Строгая инвентаризация отклоняет неполный JSON, неопределённого автора, несовпадающий video ID и повторяющиеся токены страниц. Даже успешный ответ POST не считается подтверждением: отдельная полная owner-GET инвентаризация должна вернуть ровно один авторский комментарий с совпадающими ID и текстом. Это подтверждение со стороны владельца, не независимое доказательство публичной видимости. `wave reconcile` выполняет только GET для установления наличия ровно одного комментария от точного владельца с точным текстом; отсутствие или дубликаты требуют расследования вручную.

## Допуск по квоте

До первого API GET и повторно перед необратимым резервированием цели реальный адаптер требует явную актуальную запись reviewed shared allowance и достаточный локальный остаток для ограниченного пути create/verification. Незаполненная quota DB, истёкший Pacific day, недостаток остатка и отсутствие идентифицируемого quota guard блокируют операцию. Это локальное свидетельство, не доказательство фактического остатка Google. Общий observation-only режим других клиентов не изменён.

Реальный адаптер атомарно резервирует общую квоту до первого GET: стоимость штатного create/verification плюс максимум трёх identity GET и трёх полных инвентаризаций по трём moderation status, с учётом всех разрешённых попыток. Текущая версия ограничивает каждый status десятью страницами. Если после последней допустимой страницы имеется nextPageToken, инвентаризация отклоняется целиком, а не принимается как доказательство отсутствия комментария. Повторная проверка внутри writer также строгая; durable target reservation создаётся только после неё и вложенного quota admission, непосредственно перед возможным POST. После POST исчерпание page limit или ошибка readback оставляет неопределённый исход без повторной отправки. Лимит страниц — консервативная граница допуска, не утверждение о числе комментариев. Отдельный эксплуатационный HOLD (владелец, абсолютный data root, фактическая Google quota, редакторский допуск) сохраняется.

## Необратимая защита первого комментария между журналами

После успешной read-only preflight, включая повторную строгую проверку writer, и под общим owner-lock, непосредственно **до** возможного POST, адаптер фиксирует запись в `VCM_DATA_DIR/youtube/panorama-first-comment-reservations.sqlite3` транзакцией SQLite с `synchronous=FULL`. Первичный ключ — `(channel_id, video_id)`, независимо от текста, operation ID, времени, имени журнала или новой версии плана. Operation ID и SHA текста сохраняются для привязки к исходному журналу. Повторная запись или ошибка хранилища блокирует POST. Резервирование не удаляется после успешной, отклонённой или неопределённой операции; даже остановка до фактической отправки требует отдельного разбора, не автоматического сброса. Журнал Wave Engine остаётся источником receipt/result, индекс — только необратимый барьер dispatch. Reconcile остаётся GET-only и не освобождает резервирование.

Для реального адаптера обязателен явно заданный абсолютный `VCM_DATA_DIR` канонического owner runtime. Не переносить токены и не создавать альтернативные data roots. Индекс должен сохраняться вместе с защищёнными операционными данными при резервном копировании и восстановлении; отсутствующий после утраты/переноса индекс нельзя считать доказательством отсутствия прежних отправок. Защита действует между процессами/журналами, использующими одно физическое хранилище. Она **не** доказывает глобальную сериализацию независимых компьютеров или CI runners; до production rollout требуется отдельная проверка единственного постоянного write-owner и актуального хранилища, включая старые неопределённые операции. Не активировать CI или вторую машину как writer. Ручное удаление базы, резервирования или выбор другого корня ради повторной отправки запрещены.

## Стадии редакции

Редактор заранее сверяет текущую речь проповедника, библейские места и первоисточник. Каждый комментарий должен тематически дополнять конкретную лекцию, а не повторять её описание. Оформление: обычный текст, отдельные абзацы, YouTube-native `*полужирный*` и `_курсив_`, без Markdown `**...` и без искусственных вопросов в конце.

**Только после отдельной редакционной приёмки** комментарий переводится из `REVIEW_ONLY` в `review_status=approved` в однооперационном пакете и получает актуальный `reviewed_at`. Сам факт создания черновика, GitHub issue или публикации описания видео **не является** разрешением на комментарий. Поле `reviewed_at` должно быть ISO 8601 с часовым поясом; это проверка формата, **не доказательство независимой редакционной приёмки**. OAuth-ответ должен содержать ровно одну валидную запись точного владельца без продолжения пагинации, а ID прочитанного видео должен совпадать с ID плана. Ссылка первоисточника в тексте — отдельный точный URL, не подстрока другого адреса. В пакете должна присутствовать `source_url` реальной страницы этой лекции, а та же ссылка — в теле комментария.

Предусмотрены только создание **первого** комментария и его GET-only reconciliation. Второй комментарий на том же видео, обновление, удаление, ответы, закрепление, переводы и любые иные операции здесь намеренно **не поддерживаются**. Для них требуется отдельная спроектированная и проверенная процедура; прямой вызов `commentThreads.insert` из операторского скрипта вместо Wave Engine запрещён.
