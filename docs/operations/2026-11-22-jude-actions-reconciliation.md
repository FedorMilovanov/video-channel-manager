## Ограничитель исполнения в этой ревизии

Поэтапный `lordchrist_telegraph_staged` отвергает все четыре этапа — подготовку и отправку
Telegraph и Telegram — для исходного ID Иуды и для тех же проверенных байтов статьи под другим ID.
Это срабатывает до записи state и доступа к провайдеру, даже при совпадающих release variables;
если claim уже существует, он остаётся без изменения для отдельной сверки. Просмотр статьи
остаётся доступным без обращения к провайдеру. В предпросмотре также убрана ошибочная подпись
серии Чарнока: Иуд. 1:5 — самостоятельная статья, а не выпуск Чарнока. Байт публикационной
статьи и provider payload эта правка не меняет.

После merge и CI ограничитель действует **только** в актуальном staged runtime: он не останавливает
старый запуск на другом SHA, произвольный внешний клиент, страницу с изменёнными байтами и другим
ID или ручную отправку. Он не проверяет GitHub live, занятость сегодняшнего дня и время суток,
не устанавливает provider absence и не является разрешением на публикацию. До возможного снятия
нужны отдельная reviewed PR с доказательствами разрешения исходной неоднозначности, текущая
сверка целевой страницы/Telegram/других writers и все обычные независимые гейты; нельзя снимать
HOLD одной переменной, новым именем или нулевым отчётом account scan.

## Что попросить у GitHub Support

Не отправлять обращение автоматически и не передавать токены/пароли. Владелец может сообщить:

> In `FedorMilovanov/video-channel-manager`, workflow run `43098273140`, check suite
> `116713949914` has shown `queued` with zero jobs since 2026-11-11 20:49:17 UTC. On
> 2026-11-22 around 11:06 UTC, one ordinary cancellation returned “Cannot cancel a workflow run
> that is completed”, while the REST run and check suite still reported `queued` and no conclusion.
> Please reconcile the inconsistent run/suite state and clarify the run's actual terminal status,
> whether any jobs were ever executed, and, if available, the original dispatch inputs. Preserve
> the run evidence; do not rerun it.

После ответа — независимо прочитать status/conclusion/jobs и защищённый ledger, проверить
другие возможные аккаунты/writers и текущую публичную ленту. Для новой отправки всё равно нужны
точные release bindings, редакционная/правовая приёмка, отдельная текущая авторизация,
единственный durable intent и provider readback. При неизвестном результате — только сверка,
не повтор. Отмена старого run сама по себе не разрешает новую публикацию.
