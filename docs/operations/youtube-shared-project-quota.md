# YouTube official API and shared-project quota

Applies to all registered YouTube owners and canonical API clients. This runbook does not authorize live calls or provider writes.

When the owner requests YouTube API work, use the repository-owned official YouTube Data API client/writer, not vidIQ, paid third-party search/management APIs, browser automation or a new ad-hoc client. No paid fallback or browser route without separate explicit owner permission. A Desktop Commander account is a transport selector, not a YouTube identity or quota project; verify the current owner-authorized device and distinguish an offline transport from an API refusal.

**Quota is shared by Google Cloud project, not by channel/OAuth alias.** Before live work, resolve the configured client project locally without printing credentials. Plan the smallest bounded request set; when a video ID is known use exact-ID `videos.list` (repository `get_video`), not a whole channel audit. If unknown, first use the exact upload URL/receipt or a bounded latest-upload lookup with owner channel + filename/title/date/duration checks, then exact-ID readback; do not infer from title alone. Reuse fresh verified evidence within the same bounded operation; mandatory preflight/postflight checks remain. Do not rescan all channels for one Short. Preserve provider quota for required verification.

For multiple channels sharing a Cloud project, coordinate aggregate planned units, actual dispatched requests (including failed requests), workflow/project attribution, and remaining headroom using a common project-scoped budget/stop record. Use the official [quota documentation](https://developers.google.com/youtube/data/determine_quota_cost) and actual configured limits, not assumed per-channel grants. Track each configured quota bucket separately: the current documented defaults distinguish `search.list`, `videos.insert`, and the shared quota for other endpoints; do not hard-code these defaults as the project's real allocation. Daily quotas reset at midnight Pacific Time (America/Los_Angeles), not at Moscow midnight. Treat provider `403 quotaExceeded`/`dailyLimitExceeded` as a project-wide terminal stop for new work using the affected quota bucket until a confirmed reset or approved quota grant; when the bucket is unclear, stop new calls conservatively. Record the exact reason and last result, notify other scopes, and reconcile uncertain effects before resuming. A successful owner GET does not prove that enough units remain for writes plus verification, or that a quota extension has been approved. Do not confuse quota exhaustion with per-user rate limiting, OAuth failure or Remote credits; never switch projects or accounts to circumvent quota restrictions. Avoid repeated quota probes; one bounded approved probe after the reset is sufficient. Google Cloud Console is the authority for project usage/limits; request a legitimate quota increase if needed.

The canonical clients' project quota guard records each admitted request attempt in a SQLite journal under the common absolute data directory (`data/youtube/quota/<project-number>.sqlite3`) and conservatively stops new admissions after a confirmed daily quota refusal, until the next Pacific day. The journal is local accounting, not Google's authoritative remaining balance; previously admitted/in-flight requests and other hosts/clients are not controlled by it. For unknown video IDs use `video-manager youtube recent --account <alias> --channel <exact-id> --limit 10` (one page; candidate discovery only), then verify the exact ID. A missing candidate never authorizes a full scan automatically.

## Local weighted allowances and reservations

The journal estimates the cost of each admitted attempt by its method and quota bucket, separately from its request counter. See the official table above. Resumable upload session, media and status attempts are conservatively estimated at one upload allowance each; they are not an authoritative Google usage measurement. Unknown methods are recorded as unpriced in observation-only mode and rejected when a local budget is enabled.

`video-manager youtube quota-status` is entirely local. The `google_remaining` field is deliberately null. After pausing competing operators and checking the **actual current remaining** quotas in Google Cloud Console (including outside clients), an owner/operator may explicitly enable a daily local allowance:

```text
video-manager youtube quota-configure --confirm-project-number PROJECT_NUMBER --pacific-day YYYY-MM-DD --shared UNITS --search CALLS --uploads CALLS --evidence REVIEW_REFERENCE
```

Use the actual project number, Pacific day and reviewed remaining headroom, not the defaults or a pending grant. Choose conservative additional allowances, not today's total grant; use zero for unused buckets. Evidence must be a non-secret reference. Configuration is one-time per Pacific day, cannot refill silently and rejects active reservations. Once enabled, a new Pacific day requires a new reviewed allocation before API dispatch. Until enabled, the journal observes costs and terminal stops without claiming an available provider balance.

A bounded `ProjectQuotaGuard.reserve(...)` context atomically holds units for a single operation and its verification; concurrent unreserved requests and other reservations cannot spend them. Each admitted attempt consumes its reservation, including transport failures. Unused units are released on normal/exceptional exit; a process crash leaves a conservative hold for that day rather than silently recovering it. Cross-midnight or cross-bucket consumption stops. A reservation without a configured allowance does **not** prove Google headroom.

Description and localization mutations reserve the one-shot write plus the maximum number of bounded immediate and resilient verification read attempts before dispatch. Comment creation/update reserves its one-shot mutation plus the bounded verification path (exact comment ID, at most one candidate page per moderation state per verification round). Full duplicate/owner preflight remains separate and cannot substitute a bounded candidate search for proof of absence. Explicit quota failure during comment readback cannot fall back to the write response as successful verification; reconcile the returned comment ID, never replay. Outer batch-level independent postflight, other release stages, unsupported/legacy clients and other hosts require separate coverage; these reservations do not claim complete integration or a Google quota increase. Cross-channel engineering must extend the existing client/writer/transport architecture, use an atomic shared budget and circuit-breaker across processes, and cover reads/writes, distinct error reasons, reset, concurrency and postflight reservation with offline fault tests. Keep the existing exact-ID write locks and release approvals. Coordinate with the active owner-audit and multilingual rollout issues before touching shared runtime; do not add another independent writer.
