# @lordchrist quote-v6 — исполнимый смысловой preflight (19 ноября 2026)

**Назначение:** исключить автоматическую публикацию непонятной читателю, неверно сокращённой,
несверенной с оригиналом или неправомерно используемой цитаты, даже когда
структура/CI/SHA исходной очереди зелёные. Это **публикационный HOLD**, а не
запрос на повторное отправление или ложная юридическая сертификация.

## 1. Действующее состояние и граница

- Единственный quote-v6 sender: `.github/workflows/lordchrist-quote-v6-publisher.yml`.
- Release: `quote-v6-owner-release.json`, `lordchrist-quote-v6-20261106`; frozen source и restyle-v2 **не изменялись** этой волной.
- Сверено 19.11.2026: protected `state/lordchrist-telegram/content/telegram/lordchrist/quote-v6-publication-ledger.json`: 30 записей, **12 `published/provider_effect=verified`, 18 `pending/provider_effect=impossible`**. Все опубликованные имеют Telegram message ID, в частности Бакстер #1618 и Эдвардс #1629. Эта сводка — точка во времени, а не вечная константа.
- Из 30 по редакционному triage: 12 `PASS_MEANING` только по русскому смыслу, 12 `REVIEW_REQUIRED`, 6 `HOLD_MEANING`; среди последних опубликованные Бакстер/Эдвардс и 4 pending. Triage **не равно** независимой сверке перевода и прав.
- **Ни одной** действительной независимой meaning/original/translation/rights approval для ожидающих 18 карточек пока нет в новом review register. Отправитель обязан завершиться с `SemanticApprovalHold` **до записи intent**. Не создавать новую «догоняющую» публикацию.

## 2. Две разные границы доказательств

**A.** `content/telegram/lordchrist/quote-v6-semantic-review-v1.json`:
30 точных ID, frozen original English SHA, source Russian SHA, source URL, final Telegram
payload SHA, контекст и редакционная риск-оценка. Это **редакторский запрос**:
`semantic_verdict=REVIEW_REQUIRED`, original/translation/rights status пуст/отрицателен.
Публикации в этом файле не должны внезапно становиться publishable от одного
`PASS_MEANING`.

**B.** `content/telegram/lordchrist/quote-v6-semantic-activation-v1.json`:
отдельная точная ссылка на merged PR, его `head.sha`, GitHub review ID и
логин независимого одобрившего ревьюера для каждого уже **содержательно
принятого** `publication_id`. Исходно `entries=[]`. Тесты не создают
и не авторизуют реальные допуски.

### Для реального принятия одной pending-карточки

1. Подтвердить контекст **по первичному оригиналу**, соответствие русских слов и
   выбранной редакции, грамматику и ограничения использования конкретного
   перевода/издания. Публичное доменное состояние английского автора **не
   означает** отсутствие прав на современный русский перевод.
2. В отдельном PR A заполнить в review register для **точного** ID:
   `reader_thesis`, `reasoning_link`, `reader_misreading`,
   `edition_and_rights_note` (каждое содержательно, без фиктивных строк);
   `semantic_verdict=PASS_MEANING`,
   `original_collation=independently_verified`,
   `russian_translation_review=independently_verified`,
   `rights_clearance=documented_cleared`,
   `contiguous_source_span_verified=true`. Сверить SHA финального payload
   с очередью. Если текст надо менять — **не исправлять** старый frozen
   payload: подготовить новый versioned release/state migration plan.
3. Получить **реальный APPROVED review от другого аккаунта** на точный
   `head.sha` PR A и смержить в `main`. Самоподпись автора PR, историческая
   `owner-requested` запись, зелёный CI и текст в комментарии не заменяют
   GitHub reviewer approval.
4. Отдельным PR B добавить в activation register точный `publication_id`,
   `review_pr_number`, `approved_pr_head_sha`, `reviewer_login`,
   `github_approval_review_id`. Эти поля — только указатель: работающий
   gate повторно делает **GET** PR A, reviews и `contents` точного review
   файла на `approved_pr_head_sha` и проверяет живой blob SHA. Сам PR A
   **обязан изменить этот реестр**: одобрение постороннего PR, в котором
   неизменённый JSON просто присутствовал, непригодно. Если файл поменялся
   после принятия, approval отклоняется. Увеличение числа записей activation
   не допускает публикацию другого ID.
5. Запускать единственный существующий sender **только штатным расписанием**,
   только после актуального `main` и green CI, по текущему protected ledger,
   в его существующем московском окне и при согласованных source/rights
   требованиях. Этот документ и PR не дают отдельного разрешения на отправку.
   Исторические `init`, `migrate-restyle` и `migrate-editorial-v2` **отклоняются**
   в live CLI/workflow. Не переписывать 12 опубликованных карточек и их ledger.
6. Перед `prepare_next` sender проверяет gate, а перед
   **необратимым** `sendMessage` проверяет его снова. При GitHub outage,
   отозванном review, смене payload или правах `not_cleared` — жёсткий
   отказ **без Telegram POST**. Если pre-send intent уже persisted
   и потом approval отозван, этот intent остаётся блокирующим; ручная
   reconciliation без повторной отправки обязательна.

### Что должен проверить независимый редактор

- Что утверждает автор, кому адресовано и на каком основании?
- Не исказило ли сокращение противопоставление, условность или аналогию?
- Не требуется ли соседнее предложение, без которого «сила», «рабство»,
  «христианин-воин», «довольство» или аллегорическая Беула теряют предмет?
- Верна ли русская грамматика и сопоставим ли перевод с оригиналом пословно?
- Есть ли точная ссылка на первоисточник и законное основание публикации именно
  этого текста на русском? Не выдаётся ли перевод-компиляция за речь автора?
- Ясен ли смысл читателю **до** жирного/курсива, тегов и внешнего пояснения?
- Указаны ли reviewer, его независимый PR review и exact SHA принятого документа?

**Историческая миграция 11/19 не совместима с продвинутым ledger 12/18.**
Она навсегда закрыта в текущем публичном command path. Для будущих изменений

строгой миграции `pending`-только после точного state readback и контроля
параллельных writer'ов; этот PR **не** меняет state.

## 4. QA и критерии завершения инженерной части

- Python-test: register содержит 30 уникальных source/payload-bound ID.
- Fail-closed на `REVIEW_REQUIRED`, `HOLD_MEANING`, неподтверждённом
  оригинале/русском переводе/правах, изменённом SHA, отсутствующем ID,
  отсутствующем GitHub token, несовпавшем blob PR A, отозванном review,
  review от автора самого PR.
- Positive **искусственный** сценарий с независимым APPROVED exact-head PR
  проверяет, что gate логически допускает только конкретный payload.
  Тестовый токен/PR — фиктивные и **не** открывают реальный writer.
- Integration: при отказе в `prepare` нет provider preflight, intent,
  protected state write. При отказе в `send` после persisted intent —
  нет `sendMessage` и запрещён автоматический повтор.
- Последний PR в `main`, все обязательные тесты зелёные; сравнить diff с
  `main` и обеспечить отсутствие правок квот, очереди, хроники,
  cron и Telegram bytes.

**Это не утверждение, что все 18 ожидающих публикаций содержательно
сверены и разрешены.** Инженерное закрытие — 100% запрет на необоснованную
отправку и проверяемый путь до допуска, а окончательная редакторская
приёмка — реальные внешние исследования и проверка прав, не отрабатываемые
механически.
