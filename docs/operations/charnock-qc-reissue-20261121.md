# QC-редакции Чарнока: историческое переиздание и read-only сверка

Владелец проекта: `@FedorMilovanov`, канал: `@lordchrist`. Историческая волна `20261121`
затронула 13 уже существовавших страниц; зафиксированные запуски проходили 21–22.11 UTC
(22.11 по Москве). Новые страницы и Telegram-сообщения в этом цикле не создавались.
Номера запусков и исходные результаты сохранены в
[журнале](../audits/2026-11-21-charnock-qc-reissue-execution-log.md).

**Старый исполнитель `editPage` выведен из действия.** Подтверждение
`REISSUE_EXISTING_CHARNOCK_PAGE_ONCE`, старый `--execute` или старый манифест больше не
авторизуют новую правку через текущий скрипт: `--execute` останавливается до любого GET.
Это не отключает уже запущенный старый SHA или копию вне текущего кода. Любая будущая правка
требует отдельного рассмотренного payload, актуального разрешения, durable intent до POST,
no-replay и независимого readback; эта read-only сверка их не заменяет.

Причина вывода: квитанции старого workflow лежали в отдельном временном каталоге каждого
запуска, поэтому проверка наличия файла не блокировала следующий запуск. После принятого POST
сбой публичного readback также мог завершить шаг без квитанции `UNCERTAIN`. Это нельзя
считать устойчивой межзапусковой защитой от повтора. В
[`retirement-registry-v1.json`](retirement-registry-v1.json) выведен именно режим записи,
а не read-only reader. Исторические результаты сохраняются как свидетельства, а не как
разрешение повторять их.

## Действующая read-only сверка

Workflow `.github/workflows/lordchrist-charnock-qc-reissue.yml` вызывается вручную только
владельцем на точном текущем `main`. Каждый режим выполняет один публичный GET существующей
страницы; токены Telegraph/Telegram и provider-write permissions ему не передаются. Вход
`page` выбирает ровно один ключ 01b или 02–13.

1. Исторический QC-манифест
   `content/telegram/lordchrist/telegraph-v1/charnock/charnock-qc-reissue-20261121.json`
   должен совпасть с очередью по точному `publication_id`, пути и Git blob статьи;
   загрузчик очереди проверяет локальные байты статьи и обложки по её blob-значениям.
   Если очередь изменилась, сверка останавливается, а не подменяет закреплённый источник.
2. Публичные `path`, `url`, автор и ссылка автора должны точно совпасть с закреплённой
   идентичностью. Заголовок сравнивается точно. `dry-run` и `reconcile` по-прежнему
   определяют `VISIBLE_TEXT_MATCH` только по последовательности **верхнеуровневых тегов
   и видимого текста после нормализации пробелов**. `VISIBLE_TEXT_MISMATCH` даёт ненулевой
   exit. Ограниченное совпадение не доказывает media, ссылки, вложенную разметку, пустые
   узлы или точные пробелы.
3. Отдельный режим `structural-reconcile` требует совпадения заголовка и **всего дерева
   nodes** после двух конкретных нормализаций: соседние текстовые фрагменты объединяются
   только в массивах content/children; дополнительный строковый `id` в live-заголовке
   `h3`/`h4` исключается, только если соответствующий рассмотренный заголовок не задаёт
   `id` (опустевший после исключения live `attrs` тоже удаляется). Происхождение такого
   live ID неизвестно: он может быть как сгенерированным, так и добавленным автором.
   Явно заданный в образце ID сравнивается точно, включая тип JSON; дополнительный
   нестроковый live ID не игнорируется. Остальные узлы и атрибуты, включая массивы внутри
   атрибутов, ссылки, URL изображений, типы JSON и пробелы сравниваются; `true` не равно
   `1`. `NORMALIZED_NODE_TREE_MISMATCH` даёт ненулевой exit, даже если видимый текст
   совпал. Квитанция содержит SHA-256 деревьев после попарной нормализации относительно
   рассмотренного образца и до пяти ограниченных путей отличий, без копирования значений
   и неизвестных ключей. Новый алгоритм `target-relative-heading-ids-v2` указан и в
   квитанции, и в аннотации; live-хэш зависит от образца и не является самостоятельным
   отпечатком страницы. `provider_content_exact` отдельно означает точное совпадение
   канонизированных JSON nodes до нормализации.
4. Оба режима `reconcile` пишут одну квитанцию вне Git и выгружают её даже при mismatch;
   компактная сводка статуса, проверок и хэшей также попадает в аннотацию при успехе и
   mismatch без полного текста страницы. Ошибка до создания квитанции завершает workflow
   без неё. Выбор `media_base=current-main`
   строит целевые media URL с SHA текущего main; `historical-qc-20261121` подставляет
   `c1bafa972e91d536fc56d86e53b4ce6f3502f37d` — head исторических QC запусков 02–13
   и сверки 01b. Это выбор строки URL для сравнения, **не запуск старого кода** и не
   подтверждение сохранности байтов изображений. Выбранный SHA фиксируется в результате.

Даже `NORMALIZED_NODE_TREE_MATCH` не проверяет байты по URL, доступность ссылок,
происхождение или значение исключённого live heading ID либо визуальный рендер. Ни один
результат не доказывает содержимое Telegram, независимую редакционную приёмку, отсутствие
другого writer или разрешение на миграцию/отправку. Проверка существующей страницы перед
будущим Charnock send также требует точные path/URL/заголовок/автора и использует ту же
попарную нормализацию; она не меняет ранее утверждённые release/state gates.

Исторические `structural-reconcile` запуски 45052266422, 45052322569 и 45052370264
использовали прежний алгоритм, исключавший все heading IDs, и не становятся задним числом
проверками по новым правилам. Все 13 закреплённых локальных образцов сейчас содержат 123
заголовка без явно заданного ID; это не проверка текущего live-контента или происхождения
его ID. Совпадение хэшей локальных образцов по прежнему и новому алгоритму при искусственно
добавленных строковых ID — только синтетическая проверка совместимости, не новая сверка.

Исторический `VERIFIED_REISSUE_RECONCILED` использовал более слабую проверку и сам по себе
не проверял заголовок в условии успеха. При повторном чтении аннотаций тех **13 старых**
запусков записанные `title_before` и `title_after` совпали 13/13; path и URL также совпали
с манифестом. Это проверка старых записей, а не свежая сверка всей серии. Отдельный
публичный GET №10 не включал локального сравнения всего тела; границы и конкретные run IDs —
в журнале.

## Не смешивать с Telegram-перевыпуском

Исторический incident-манифест 06–13 и исходные receipts не менялись. №09 уже имеет
terminal receipt и не должен повторяться; №06–08 требуют отдельно утверждённых дат;
№10–12 остаются заблокированы source-binding drift; №13 остаётся на редакционном HOLD.
Требуются отдельно рассмотренная миграция идентичности и отдельная авторизация исполнения,
а не замена исторических SHA. Страницы 04/05 не увеличивать без сокращения.
