# Проверенные цитаты и GitHub-публикатор для @lordchrist

Дата: 2026-08-06  
Проект: `lord-god-strength`  
Поверхность: Telegram-канал `@lordchrist`  
Owning issue: `#141`

## Точное состояние

- Редакционный корпус: **30 публикаций**.
- Включены только классические авторы, чьи использованные английские тексты находятся в общественном достоянии.
- Для каждой публикации зафиксированы автор, точный труд, место в тексте, первичная страница и английские якоря начала и конца.
- Каждый русский блок является переводом одного непрерывного выбранного фрагмента без внутренних пропусков.
- Резерв, GraceGems-компиляции, Goodreads, сайты с цитатами, пересказы, синтезы и редакторские вставки удалены.
- Современные авторы не включены в эту строгую месячную очередь: длинный многабзацный материал по ним требует отдельного режима цитирования и отдельного авторско-правового решения.
- Текущий provider-effect: `not_dispatched`. Создание кода, очереди, тестов и PR не отправляет сообщений в Telegram.

Канонические файлы:

- `content/telegram/lordchrist/verified-30-posts.json` — неизменяемая машинная очередь;
- `content/telegram/lordchrist/verified-30-posts.md` — проверочный документ для человека;
- `src/video_channel_manager/telegram_publisher.py` — единственная бизнес-реализация;
- `scripts/telegram/post_next.py` — тонкий CLI;
- `.github/workflows/lordchrist-telegram-poster.yml` — облачный оркестратор;
- ветка `state/lordchrist-telegram` — отдельный долговечный журнал публикаций.

## Почему состояние не коммитится в main

Код и утверждённая очередь в `main` неизменяемы. Текущий статус публикаций хранится только в ветке `state/lordchrist-telegram` в файле:

```text
content/telegram/lordchrist/publication-ledger.json
```

Это даёт четыре преимущества:

1. ежедневная публикация не засоряет историю `main`;
2. изменения кода не конфликтуют с коммитами состояния;
3. workflow сначала сохраняет намерение в удалённой state-ветке и только затем вызывает `sendMessage`;
4. после тайм-аута или падения runner удалённое состояние остаётся блокирующим и не позволяет слепо отправить тот же пост повторно.

## Модель безопасности

Перед отправкой выполняются следующие проверки:

1. очередь содержит ровно 30 карточек и проходит Pydantic-валидацию;
2. SHA-256 очереди точно совпадает с repository variable `LORDCHRIST_APPROVED_QUEUE_DIGEST`;
3. `getMe` возвращает ожидаемого бота;
4. `getChat` разрешает `@lordchrist` в ожидаемый числовой `chat_id`;
5. `getChatMember` подтверждает статус администратора и право `can_post_messages`;
6. первый ещё не опубликованный элемент находится строго по порядку;
7. в state-ветку коммитится состояние `dispatching / may_exist` с уникальным `intent_id`;
8. workflow повторно читает этот коммит из удалённой state-ветки и сверяет его с подготовленным конвертом;
9. только после этого вызывается `sendMessage`;
10. успех признаётся только при совпадении возвращённых `chat.id`, полного текста и положительного `message_id`.

Если ответ Telegram потерян после отправки, запись становится `unknown / may_exist`. Следующие публикации и повтор этой публикации блокируются до ручной сверки. Автоматического blind retry нет.

## Расписание

Workflow делает два облачных пробных запуска ежедневно:

```text
09:17 Europe/Moscow
21:17 Europe/Moscow
```

Второй запуск — только страховочный. Код разрешает не более одной подтверждённой публикации на календарную дату Москвы. Если утренний запуск уже опубликовал пост, вечерний завершится без provider-вызова.

Домашний компьютер, `telegram-bot-api.exe` и MP3-бот для текстовых публикаций не нужны. GitHub Actions обращается к официальному облачному Bot API.

## Обязательная настройка GitHub

### Secret

```text
LORDCHRIST_TELEGRAM_BOT_TOKEN
```

Используется отдельный бот, созданный через BotFather и добавленный администратором канала с правом публикации. Токен никогда не записывается в репозиторий, журнал или URL ошибки.

### Repository variables

```text
LORDCHRIST_TELEGRAM_CHAT_ID=-100...
LORDCHRIST_TELEGRAM_BOT_USERNAME=имя_бота_без_@
LORDCHRIST_APPROVED_QUEUE_DIGEST=sha256:43518f50844b92230dd3854c363e86f0075347e31ed266f0ecad9c92b48d1b20
LORDCHRIST_POSTING_ENABLED=false
LORDCHRIST_SCHEDULE_ENABLED=false
```

Числовой `chat_id` не угадывается и не заменяется одним username. Он должен быть получен и один раз проверен через read-only preflight.

## Порядок включения

1. Сначала оставить обе переменные включения в значении `false`.
2. Запустить действие `validate` — только локальная проверка очереди и state-ветки.
3. Запустить `preview` — показать следующий пост без Telegram-запроса.
4. Добавить отдельного бота в `@lordchrist`, настроить secret и точные переменные идентичности.
5. Установить `LORDCHRIST_POSTING_ENABLED=true`, но оставить `LORDCHRIST_SCHEDULE_ENABLED=false`.
6. Запустить `send-next`, вписав подтверждение `SEND`. Это единственный ручной canary.
7. Открыть канал и проверить полный текст и `message_id`, записанный в state-ветку.
8. Только после подтверждённого canary установить `LORDCHRIST_SCHEDULE_ENABLED=true`.

Даже если schedule включён ошибочно раньше canary, код остановится: автоматический режим требует уже существующей публикации `manual / verified` тем же ботом в том же канале.

## Ручная сверка неизвестного результата

При `unknown / may_exist` нельзя повторно нажимать `send-next`.

Доступны три явных действия:

- `resolve-published` — сообщение найдено в канале; требуется точный `message_id` и подробная evidence note;
- `resolve-absent` — отсутствие сообщения подтверждено ручной сверкой; только это действие возвращает элемент в `pending`;
- `skip` — элемент сознательно снимается с очереди.

Для каждого действия требуется подтверждение `RESOLVE`. Любое решение сохраняется в отдельной state-ветке с именем пользователя GitHub и пояснением.

## Ограничения GitHub Actions

- расписание выполняется только из workflow, находящегося в default branch;
- запуски сериализованы через одну concurrency-группу с `queue: max`;
- очередь кода и state-ветка должны существовать до первого исполнения;
- в публичном репозитории GitHub может отключить scheduled workflows после 60 дней отсутствия активности; ручной `workflow_dispatch` остаётся способом проверить и снова включить процесс;
- редактирование текста любой карточки меняет digest и автоматически блокирует отправку до нового явного утверждения digest.

## Точный postcondition

Одна операция считается завершённой только тогда, когда удалённая state-ветка содержит:

```text
state = published
provider_effect = verified
message_id > 0
actual_chat_id = ожидаемый LORDCHRIST_TELEGRAM_CHAT_ID
bot_id = идентификатор проверенного бота
payload_sha256 = digest неизменяемого поста
```

HTTP 200, зелёный workflow, строка stdout или наличие локального коммита сами по себе не являются достаточным доказательством публикации. Явный ответ Telegram 4xx/429 фиксируется как `confirmed_absent`; сетевой обрыв после начала передачи — как `may_exist`, без слепого повтора.
