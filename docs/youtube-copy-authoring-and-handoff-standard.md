# YouTube copy authoring and handoff standard — The Legendary Poet

Статус: обязательное авторское дополнение к существующим YouTube-стандартам проекта.

Этот документ фиксирует правила подготовки описаний и закреплённых комментариев **до** provider-write: как исследовать материал, писать текст, передавать его человеку для копирования и не терять YouTube-разметку `*...*` / `_..._` в интерфейсе чата или PowerShell.

Он не заменяет и не ослабляет существующие источники истины:

1. `docs/operations/project-identity-registry.md` — точные project/channel IDs и публичные маршруты;
2. `docs/youtube-editorial-standard.md` — тип контента, названия, плейлисты, фактчекинг и approval boundary;
3. `docs/youtube-description-rendering-standard.md` — точная YouTube-разметка, пунктуация, первый абзац, URL и layout;
4. `docs/youtube-comment-editorial-standard.md` — отдельный стандарт top-level / pinned comments;
5. этот документ — авторский workflow, качество текста и безопасная передача готового copy.

Если формулировки расходятся, более узкий канонический документ выше по списку имеет приоритет. В частности, ссылки нельзя копировать из старой памятки вслепую: для нового вывода используются текущие project routes из registry/profile.

## 1. Готовый handoff человеку

Если пользователь просит **готовое описание, закреп или текст для вставки**, итоговый copy выдаётся внутри одного fenced-блока `text`.

Причина: интерфейс чата не должен съедать или визуально применять `*жирное*` и `_курсив_` до копирования.

Правильно:

```text
*Название произведения*
_важный образ_
```

Нельзя экранировать эти маркеры обратным слешем:

```text
\*текст\*
\_текст\_
```

Если пользователь запросил только финальный copy, вокруг блока не добавляются объяснения, советы и служебные строки. Несколько вариантов — несколько отдельных блоков `text`.

Этот handoff-rule относится к представлению ответа человеку и не является синтаксисом YouTube API.

## 2. Содержательная планка

Описание должно быть полностью готово к прямой вставке в YouTube Studio и при этом оставаться литературным текстом, а не SEO-заготовкой.

Обязательно:

- один смысловой абзац развивает одну новую мысль;
- конкретный образ, конфликт, исторический факт, ритм или художественное решение важнее общих эпитетов;
- текст уважителен к автору и первоисточнику;
- историческая точность важнее красивой формулировки;
- интерпретация явно отделяется от проверяемого факта;
- описание музыкальной/визуальной версии называет конкретные художественные решения, а не рекламные клише.

Не превращать описание в анкету из повторяющихся рубрик `Главный смысл:`, `История создания:`, `Почему стоит послушать:` без прямого запроса пользователя.

## 3. Антишаблонный словарь

Не использовать как универсальные заготовки:

- «Это не просто стихотворение...»;
- «Это настоящее путешествие...»;
- «Произведение заставляет задуматься...»;
- «Уникальная атмосфера...»;
- «Глубокий смысл...»;
- «Вечные вопросы...»;
- «Шедевр русской литературы...»;
- «Ожившая классика...»;
- «Никого не оставит равнодушным...»;
- «современное звучание классики»;
- «новое прочтение великого произведения»;
- «уникальное сочетание прошлого и будущего»;
- «нейросети оживили поэзию».

Сильное определение должно быть подтверждено конкретным наблюдением. Не злоупотреблять словами `пророческий`, `гениальный`, `великий`, `вечный`, `уникальный`, `невероятный`, `мощнейший`, `глубочайший`.

## 4. Исследование до написания

Если copy содержит сведения об авторе, произведении, истории создания, датировке, публикации, посвящении, биографии, цитате или предполагаемом авторском замысле, сначала проводится исследование.

Приоритет источников:

1. полные собрания сочинений и академические издания;
2. авторские письма, дневники и записные книжки;
3. первые публикации и прижизненные издания;
4. государственные архивы, музеи и библиотеки;
5. академические комментарии;
6. научные статьи и монографии признанных исследователей;
7. надёжные энциклопедические и образовательные ресурсы.

Для русской литературы в первую очередь использовать академические издания, ФЭБ, РВБ, НЭБ, РГБ, Пушкинский Дом, литературные музеи и проверенные электронные собрания сочинений.

Не строить фактологическую часть на случайных блогах, SEO-статьях, анонимных сайтах, школьных сочинениях и цитатниках. Важные даты и спорные сведения по возможности подтверждать двумя независимыми надёжными источниками. Цитаты сверять с первоисточником.

Не писать как факт: `Есенин однозначно имел в виду...`, `Блок хотел сказать...`, `Автор предсказал...`, если это не доказано источниками.

Безопасные формулы интерпретации:

- `Этот образ можно прочитать как...`;
- `В стихотворении возникает ощущение...`;
- `Такое сопоставление позволяет увидеть...`;
- `Это не обязательно прямой авторский замысел, но такой смысловой слой возникает из образов произведения.`

В публичное описание библиографию автоматически не вставлять: evidence остаётся редакционным основанием, а не рекламным хвостом.

## 5. Первый абзац описания

Первый абзац — share-preview boundary и должен соответствовать `youtube-description-rendering-standard.md`.

Обязательно:

- без `*` и `_`;
- без списка ссылок;
- без тяжёлой справочной рубрикации;
- обычно 2–4 предложения;
- сразу даёт конкретный вход в произведение и его напряжение;
- не повторяет механически title;
- не звучит как рекламный анонс.

После первого абзаца разрешены умеренные `*жирные*` и `_курсивные_` акценты.

## 6. Разметка YouTube

Используются только конструкции, которые реально проходят в YouTube copy:

- `*текст*` — жирное;
- `_текст_` — курсив;
- `-текст-` — зачёркивание, когда оно действительно нужно;
- открытые `https://...` URL;
- таймкоды `00:00`, `01:27`, `03:45`;
- простые буллеты `•`, `▸`, `→`.

Не использовать в готовом YouTube copy:

- Markdown-заголовки `#`, `##`, `###` как структуру текста;
- HTML;
- Markdown-таблицы;
- `[название](https://...)`;
- обратные слеши для экранирования `*`, `_` или `#`;
- декоративные линии без прямой редакционной причины.

Хэштег `#TheLegendaryPoet` — это хэштег, а не Markdown-заголовок.

## 7. Пунктуация и обёртки

Точный приоритет имеет `youtube-description-rendering-standard.md`.

Короткое правило: если знак завершает выделенную фразу, он входит внутрь обёртки.

Правильно:

```text
*боль,*
*свет.*
*«О, Русь моя! Жена моя!»*
_«Покой нам только снится...»_
*Плейлист «Поющие Поэты»:* https://...
*VK:* https://...
```

Неправильно:

```text
*боль*,
*свет*.
*«Покой нам только снится»*...
*VK*: https://...
```

Но внешняя синтаксическая пунктуация остаётся снаружи. Линтер не должен механически переносить неоднозначный знак без контекста.

Внутри края обёрток нет пробелов. Обёртки парные, не пересекаются и не захватывают URL.

## 8. Внутренняя логика длинного описания

Это не обязательные видимые рубрики, а порядок мышления редактора:

1. первый абзац — тема, настроение и центральное напряжение;
2. краткий контекст произведения;
3. один-два действительно важных исторических факта;
4. центральные образы и внутренний конфликт;
5. сложная строка/образ, если зрители часто понимают её слишком упрощённо;
6. конкретные особенности музыкальной или визуальной интерпретации;
7. философский/духовный слой только когда он уместен и не подменяет авторский замысел;
8. сильное завершение, возвращающее к главному образу;
9. блок канала, релевантных плейлистов и project links;
10. хэштеги.

Не пересказывать стихотворение строфа за строфой без отдельного запроса и не превращать описание в биографическую статью.

## 9. Музыкальная и визуальная интерпретация

Вместо рекламных формул описывать конкретику:

- характер и регистр голоса;
- темп, нерв, паузы и кульминации;
- важные инструменты;
- переход от одной драматургической фазы к другой;
- монтаж, цвет, свет, движение камеры;
- историческую или символическую среду.

AI не объявляется «улучшившим» оригинал. Результат описывается как интерпретация, эксперимент или попытка услышать заложенную в тексте драматургию.

## 10. Плейлисты и project links

Добавлять только ссылки, относящиеся к конкретному ролику. Не перегружать описание всеми плейлистами канала.

Точные playlist IDs и project routes берутся из текущего `youtube-editorial-standard.md` и `project-identity-registry.md`, а не из памяти чата или старой памятки.

Это особенно важно для VK: legacy `vk.com` может существовать как compatibility input, но новый канонический output должен следовать текущему profile/registry.

Открытые URL остаются обычным текстом; подпись может быть выделена:

```text
*Плейлист «Сергей Есенин»:* https://...
*VK:* https://...
*Telegram:* https://...
*RUTUBE:* https://...
```

## 11. Хэштеги

Используются только релевантные хэштеги, без SEO-мусора и дублирующих форм одного и того же слова.

Авторская памятка допускает ориентир **10–18** релевантных хэштегов для насыщенного long-form copy. Это **не hard invariant** и не должно автоматически навязываться линтером: конкретный editorial profile или ручное решение может использовать меньше. Обязательный брендовый тег, когда хэштеги используются: `#TheLegendaryPoet`.

После блока хэштегов не добавлять служебные пояснения.

## 12. Закреплённый комментарий

Pinned/top-level comment не является вторым описанием и дополнительно подчиняется `youtube-comment-editorial-standard.md`.

Авторский ориентир:

- заметно короче описания;
- обычно 500–1500 символов, если нет другого лимита;
- не повторяет описание дословно;
- даёт дополнительный факт, иной ракурс или точное наблюдение;
- вопрос/призыв не добавляется автоматически;
- если вопрос нужен, он связан с конкретной строкой, образом, версией или фактом;
- фактологический закреп остаётся фактологическим и не получает искусственный философский финал.

В закрепе форматирование разрешено с первой строки; правило plain first paragraph относится к description share-preview, а не к comment.

## 13. Автоматизация: что можно и нельзя проверять машиной

Детерминированный validator может блокировать или предупреждать о механически доказуемых проблемах:

- форматирование в первом абзаце;
- незакрытые `*` / `_`;
- пробелы внутри края обёрток;
- Markdown-links вместо открытых URL;
- лишние пустые строки;
- слишком длинные плотные абзацы;
- механическую emoji-density;
- безопасно доказуемые ошибки punctuation scope;
- неверные project routes, если они проверяются registry-bound валидатором.

Автоматизация не должна сама «улучшать»:

- исторические факты;
- даты и посвящения;
- литературную интерпретацию;
- спорную пунктуацию;
- художественные эпитеты;
- выбор того, что считать главным смыслом произведения.

Это human editorial boundary.

## 14. Финальный preflight copy

Перед передачей текста человеку или включением в immutable provider-write plan проверить:

1. copy готов к прямой вставке в YouTube;
2. при ручном handoff он находится в блоке `text`;
3. `*` и `_` не экранированы обратными слешами;
4. первый абзац description plain-text;
5. все обёртки закрыты и без edge spaces;
6. пунктуация соответствует смысловой границе выделения;
7. нет Markdown-links, HTML и таблиц;
8. нет шаблонной рекламной воды;
9. каждый абзац добавляет новую мысль;
10. факты имеют evidence и цитаты сверены;
11. интерпретация не выдана за доказанный авторский замысел;
12. плейлисты и project links относятся к точному ролику;
13. URLs открытые и соответствуют текущему registry/profile;
14. соблюдён platform character limit с запасом;
15. хэштеги релевантны;
16. текст не требует ручного исправления после копирования;
17. provider write всё равно требует отдельного immutable plan и явной авторизации.

## 15. Применение к новым публикациям

Для нового long-form ролика The Legendary Poet редакционный pipeline должен быть:

```text
research/evidence
→ draft без шаблонов
→ YouTube authoring review
→ deterministic description lint
→ human-readable preview в fenced text block
→ exact metadata plan
→ separate provider-write authorization
→ post-write readback
```

Наличие качественного текста не является разрешением на remote mutation.
