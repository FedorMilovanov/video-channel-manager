# Исследование: техническая возможность нативных карточек VK и разбор ошибок (2026-08-03)

## 1. Главный вердикт
Технически нативные карточки со встроенным фото-превью (когда VK сам формирует и раскрывает карточку внешней ссылки) в актуальном API VK **возможны** и поддерживаются.

Метод работы с карточками основан на официальном контракте VK API:
1. Предварительный сброс кэша внешнего краулера через `pages.clearCache`.
2. Подготовка и разбор вложения через `wall.parseAttachedLink` с передачей пользовательского токена и массива объектов `links=[{"type":"link","link":"URL"}]`.
3. Извлечение параметров сформированной карточки (`link_title`, `link_photo_id` вида `ownerId_photoId`).
4. Отправка поста через `wall.post` только после подтверждения наличия фото в распарсенной карточке.

## 2. Разбор 5 ключевых ошибок в предыдущих попытках

### Ошибка 1: Передача сырого URL напрямую в `wall.post`
При первоначальных попытках внешний адрес сайта (`https://gospod-bog.ru/...`) передавался в параметр `attachments` метода `wall.post` без предварительной подготовки карточки.  
**Результат VK:** ошибка `Violated: link_photo_sizing_rule. No photo given`.  
**Причина:** Начиная с сентября 2025 года VK ужесточил правила прикрепления внешних ссылок. Одного URL недостаточно — VK требует либо предварительно сформированную внутреннюю карточку со встроенным фото, либо отдельно загруженное фото-вложение.

### Ошибка 2: Некорректный JSON-массив в `wall.parseAttachedLink`
При первых тестах `wall.parseAttachedLink` в параметр `links` отправлялся массив вида:
```json
[{"url": "https://gospod-bog.ru/..."}]
```
Вместо требуемой спецификацией схемы:
```json
[{"type": "link", "link": "https://gospod-bog.ru/..."}]
```
Из-за неверной структуры VK возвращал пустой массив `data: []`, после чего был сделан ошибочный вывод, что метод недоступен для данного домена или токена.

### Ошибка 3: Ожидание одноэлементного объекта в ответе `data`
Код первоначально предполагал, что в `data` приходит один словарь с описанием ссылки. Официальная схема VK 5.199 определяет `data` как **массив вложений**, где помимо объекта с `"type": "link"` могут находиться служебные элементы. В текущих модулях этот момент исправлен: код ищет единственное вложение типа `link` с совпадающим URL.

### Ошибка 4: Отсутствие вызова `pages.clearCache` перед парсингом (критическая находка)
У VK существует официальный метод `pages.clearCache`, который очищает кэш внешних страниц для краулера `vkShare`.  
В предыдущих экспериментах после изменений Open Graph метаданных сайта метод `pages.clearCache` **не вызывался**. В результате `wall.parseAttachedLink` продолжал отдавать старое сохранённое в кэше VK состояние страницы (без фото или с ошибкой парсинга).

### Ошибка 5: Досрочный отказ от нативного пути до проверки кэша и WebP
Отрицательный вывод о невозможности нативных карточек был сделан до проверки последовательности `pages.clearCache -> wall.parseAttachedLink`. Кроме того, остался неизолированным фактор формата изображения: сайт использует `.webp` для `og:image`. Если краулер VK не поддерживает WebP для генерации превью, следующим шагом является проверка `.jpg` (1200×630) в `og:image` после сброса кэша.

## 3. Статус Open Graph сайта `gospod-bog.ru`
Аудит метаданных первой статьи (`rimlyanam-7`) подтверждает:
- Точные `og:title`, `og:description`, `og:url`;
- Canonical-ссылка совпадает с целевым адресом;
- Тег `robots = index, follow, max-image-preview:large`;
- Изображение объявлено размером `1200×630`;
- Формат изображения сейчас указан как `og:image:type = image/webp`.

**Рекомендация по сайту:**  
Если read-only проверка (`vk_native_link_preview_probe.ps1` или `vk_native_preview_auto_canary_v5.ps1 -Mode Probe`) вернёт карточку без `photo_id`, для тестовой статьи №1 следует заменить изображение в `og:image` на JPEG 1200×630, выполнить `pages.clearCache` и повторить парсинг.

## 4. Архитектура безопасной проверки (v5)

Созданные скрипты (`vk_native_link_preview_probe.ps1` и `vk_native_preview_auto_canary_v5.ps1`):
- **Не затрагивают** активный производственный контур фото-волны v4 (`lord-god-article-wave-v4`);
- **Не вызывают** методы `photos.*`;
- **Безопасно проверяют** токен пользователя VK без вывода его в консоль;
- В режиме `-Mode Probe`: выполняют только `pages.clearCache` и `wall.parseAttachedLink` для всех 10 статей и сохраняют отчёт без каких-либо изменений на стене;
- В режиме `-Mode AutoCanary`: создают ровно 1 отложенный тестовый пост **только если** у первой статьи подтверждено встроенное фото (`link.photo`), проверяют структуру вложений через `wall.getById` и сразу удаляют тестовую запись через `wall.delete`.
