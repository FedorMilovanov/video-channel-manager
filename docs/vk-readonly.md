# VK: безопасная read-only инвентаризация

Дата: **25 июля 2026 года**  
Статус: **реализовано в `feature/vk-readonly-v1`; удалённые изменения отсутствуют**.

## Что уже умеет модуль

```powershell
video-manager vk login --account legendary-poet
video-manager vk accounts
video-manager vk communities --account legendary-poet
video-manager vk scan --account legendary-poet --community <id-or-screen-name>
```

Модуль:

- импортирует пользовательский VK access token через скрытый ввод, локальный файл или переменную окружения;
- проверяет токен вызовами `users.get`, `video.get` и `groups.get` до постоянного сохранения;
- показывает сообщества, где пользователь является модератором, редактором или администратором;
- читает сообщество, все доступные видео, видеоальбомы и связи `видео ↔ альбом`;
- включает системные альбомы в снимок, но помечает их как системные и не считает редакционными коллекциями;
- экспортирует тот же версионированный `AuditPackage`, что и YouTube-модуль;
- не вызывает ни одного изменяющего метода VK API.

## Почему нужен пользовательский токен

Официальная схема VK API 5.199 указывает `access_token_type: user` для ключевых методов видео:

- `video.get`;
- `video.getAlbums`;
- `video.getAlbumsByVideo`;
- будущих операций `video.edit`, `video.addToAlbum`, `video.removeFromAlbum`.

Токен сообщества нельзя считать универсальной заменой пользовательскому токену. Даже при выданных разрешениях отдельные методы VK возвращают ошибку `27` — «method is unavailable with group auth». Поэтому текущий модуль сознательно принимает только пользовательский токен и проверяет его реальными read-only вызовами.

Основные права для нашего сценария:

- `video` — чтение видео и альбомов;
- `groups` — получение управляемых сообществ.

Поле `scopes` в локальном JSON фиксирует ожидаемые права, но окончательной проверкой считается успешный ответ VK API, а не текстовое заявление о scope.

## Получение и импорт токена

Создайте приложение VK подходящего типа и получите **пользовательский** access token через официальный OAuth-поток. Не вводите логин и пароль VK в Video Channel Manager: приложение их не запрашивает и не хранит.

Затем запустите:

```powershell
video-manager vk login --account legendary-poet
```

В скрытое поле можно вставить:

1. только access token;
2. полный redirect URL вида `...#access_token=...&expires_in=...&user_id=...`;
3. JSON, ранее сохранённый самим Video Channel Manager.

Для локального файла:

```powershell
video-manager vk login --account legendary-poet --token-file .\secrets\vk-token.txt
```

Для сознательной замены существующего токена:

```powershell
video-manager vk login --account legendary-poet --force
```

При `--force` новый токен сначала проверяется во временном каталоге. Невалидный токен не перезаписывает рабочий.

## Где хранятся данные

Секретный токен:

```text
data/secrets/vk/legendary-poet.json
```

Несекретный реестр аккаунтов:

```text
data/vk/accounts.json
```

Экспорт:

```text
data/exports/vk-<account>-<community-id>-<timestamp>.json
```

Каталог `data/` исключён из Git. Токен отправляется VK методом `POST` в теле запроса и не включается в URL, сообщение ошибки, `AuditPackage` или реестр аккаунтов.

## Модель идентификаторов

У VK ID видео уникален только вместе с владельцем. Поэтому канонический `remote_id` хранится в форме:

```text
<owner_id>_<video_id>
```

Для сообщества `owner_id` отрицательный. Пример:

```text
-123456_789
```

Такой ID одновременно подходит для:

- устойчивого ключа в `AuditPackage`;
- ссылки `https://vk.com/video-123456_789`;
- будущего точного `ChangePlan` без угадывания владельца.

## Что попадает в AuditPackage

### Сообщество

- числовой `community_id`;
- название, описание, screen name и URL;
- исходный ответ `groups.getById` в `metadata`;
- отрицательный `owner_id`.

### Видео

- точный `owner_id_video_id`;
- название и описание;
- длительность и дата публикации;
- приватность/обработка;
- лучшая доступная обложка;
- исходные `width` и `height`;
- поле VK `type`;
- `is_short_video=true`, когда VK возвращает `type=short_video`;
- число просмотров и другие доступные поля в `metadata`;
- SHA-256 revision от нормализованного ответа API.

### Альбомы

- точный album ID;
- название, количество видео, дата обновления;
- `is_system`;
- права `can_edit`, `can_delete`, `can_upload`, когда VK их возвращает;
- revision.

### Связи

Для каждого альбома выполняется отдельная пагинированная выборка `video.get(owner_id, album_id)`. Позиция сохраняется в порядке от старых к новым (`sort_album=1`).

## Shorts и клипы

VK уже возвращает тип видео, включая `short_video`. Это сильнее эвристики по названию, хэштегу или длительности. Поэтому:

1. `type=short_video` считается прямым признаком короткого формата;
2. `width` и `height` сохраняются для проверки ориентации;
3. обычное видео не превращается в short только из-за короткой длительности;
4. будущая межплатформенная сверка не должна автоматически приравнивать YouTube Shorts и VK Clips без сопоставления контента.

## Пагинация и устойчивость

- `video.get`: до 200 элементов на страницу;
- `video.getAlbums`: до 100 альбомов на страницу;
- `groups.get`: до 1000 сообществ на страницу;
- используются `count + offset`, пока не достигнут заявленный `response.count`;
- повторяются только временные ошибки VK `6`, `9`, `10`, `29` и HTTP `429/5xx`;
- ошибки доступа, неверного токена и параметров не маскируются повторными запросами;
- токен никогда не копируется из `request_params` VK в текст исключения.

## Системные альбомы

`video.getAlbums(..., need_system=1)` нужен для полного снимка, но системный альбом — не то же самое, что редакционный плейлист YouTube. В `AuditPackage.metadata` явно записано:

```json
{
  "system_albums_included": true,
  "system_albums_are_not_editorial_collections": true
}
```

Аудитор обязан исключать системные альбомы из рекомендаций по переименованию, удалению и тематической структуре.

## Текущие ограничения

- модуль не создаёт OAuth-приложение и не просит пароль VK;
- автоматический browser callback пока не реализован: импортируется уже полученный токен или redirect URL;
- записи, загрузки, редактирование, перемещение и удаление отключены;
- скачивание оригиналов видео не входит в read-only API-инвентаризацию;
- точное сопоставление YouTube ↔ VK будет отдельным этапом после получения обоих реальных `AuditPackage`;
- фактические ответы VK могут отличаться от опубликованной схемы, поэтому каждый новый тип ответа сохраняется в `metadata`, а критические предположения покрываются тестами.

## Следующие безопасные этапы

1. Получить первый реальный VK `AuditPackage`.
2. Сравнить видео и альбомы с YouTube-снимком по ID, названию, длительности, дате и локальным исходникам.
3. Сформировать read-only отчёт: отсутствующие публикации, дубли, неверные альбомы, Shorts/Clips, слабые названия и описания.
4. Подготовить отдельный проверяемый `ChangePlan`.
5. Только затем проектировать write-scopes, dry-run, expected revision, идемпотентность, журнал операций и откат.
